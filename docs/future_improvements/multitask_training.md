# 多任务训练冲突与任务特征分配

## 状态

- 当前状态：`基线已功能性验证，改进尚未执行`
- 优先级：`P2`
- 进入条件：各单任务的数据和基线指标已经可信

G7 已按当前 Harness 通过。G8 run5 已完成固定两卡、两 epoch、8 个全局 optimizer steps，manifest、Harness 和运行证据均已建立，结论为“功能性恢复通过”；位级 `exact_resume` 仍未通过。本文中的动态平衡和特征分配仍是后续研究假设，尚未执行，不得回写或混入已验证的 G8 基线。

## 问题背景

不同任务对视觉特征的要求并不相同：

```text
检测：局部边界和小目标
球场线/关键点/标定：精确几何
ReID：人物身份与外观
视频语义/解说：高级事件语义和时间关系
```

共享 backbone 可以互相促进，也可能造成梯度冲突。当前固定 loss 权重和采样比例是否合理，需要测量后再判断。

## 第一阶段：先观察，不改算法

每个训练 step 或固定间隔记录：

- 各任务 loss 的原始值和加权值。
- 每个任务的数据采样次数。
- 共享 backbone 的梯度范数。
- early、late 和 temporal 层接收到的梯度。
- 单任务与多任务验证指标差异。

检查配置中的 loss 权重、batch size 和学习率是否与实际优化器一致。

## 第二阶段：特征分配消融

比较：

- 几何任务使用 early 特征。
- 语义任务使用 late/global 特征。
- 检测使用 early、late 或 both。
- 任务专用 LayerNorm、projection 或轻量 adapter。

目标是在不复制完整 backbone 的情况下减少任务之间的直接干扰。

## 第三阶段：动态平衡

只有观察到明确冲突后，再评估：

- 按损失尺度调整权重。
- GradNorm 等动态 loss weighting。
- PCGrad 等梯度冲突处理。
- 按任务分阶段训练或交替训练。

这些方法会增加复杂度，不能代替数据和优化器正确性检查。

## 实验原则

- 保留单任务上限作为参照。
- 每次只改变一个共享策略。
- 所有任务使用相同数据版本和评估协议。
- 同时报告平均收益和最差任务退化，不能只看总 loss。

## 风险

- 多任务训练的结果容易受采样比例和随机种子影响。
- 动态加权可能只平衡数值尺度，不一定解决语义冲突。
- 任务专用模块过多会削弱共享 backbone 的意义。
