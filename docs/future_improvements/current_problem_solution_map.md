# SoccerMaster 当前问题与解决方向

这份文档只记录目前最重要的问题和对应解决方向。具体实验、指标和证据放在各实验报告中。

## 解说

### problem：单条参考解说不足以覆盖 30 秒内的全部重要事件

MatchTime 的一条参考解说通常只描述一个主要事件。长期使用这种监督，会让模型学会只输出一句安全而简短的解说。模型即使补充了视频中的真实事件，也可能因为与原参考不同而被传统文本指标惩罚。

**sol：**

让 AI 先看完整视频，按时间列出重要事件；看不清时补看连续画面。事实确认后，再生成使用 `[PLAYER] ([TEAM])` 等占位符的英文解说，并由人工审核。先验证新解说是否覆盖更多真实事件且没有增加编造，再考虑用少量审核数据微调模型。

### problem：现有标准无法把“遗漏、编造、说错结果和顺序错误”分开

BLEU、METEOR、ROUGE-L、CIDEr 主要衡量生成文本和参考文本是否相似。参考本身不完整时，它们无法判断新增内容是真实补充还是幻觉，也不能可靠评价事件顺序。

**sol：**

先建立视频事实表，再分别统计：遗漏了多少事件、编造了多少事件、动作结果是否正确、人物和球队是否正确、事件顺序是否正确。文本相似度只作为语言质量的辅助指标。

### problem：30 帧稀疏采样可能漏掉短动作

30 秒只采 30 帧时，触球、犯规接触和射门瞬间可能只出现一帧，甚至完全没有被采到。

**sol：**

先用稀疏帧浏览完整 30 秒，再对疑似事件附近补采连续帧。比较原始均匀采样和“稀疏浏览 + 局部密集采样”谁能识别更多真实短动作。

### problem：论文已证明 backbone 能完成基础任务，但更细的事件理解能力仍然未知

论文已经通过正式任务头证明 SoccerMaster 可以完成人物检测与属性识别、球场线和关键点检测、基础事件分类以及视频—文本对齐。因此，不需要再用小 probe 重复测试这些能力。但现有结果还不能说明模型能否理解一个片段中的多个事件、事件起止时间，以及“谁做了什么、结果如何”。

**sol：**

不再测试论文已经覆盖的基础任务，只补充五项测试：多事件识别、事件开始和结束时间、主体与动作绑定、动作结果、事件顺序。冻结 backbone，使用简单任务头读取这些信息；如果简单任务头已经能在新比赛上识别，就直接检查 Q-Former、Llama 和解码阶段，不再增加更重的任务头。如果逐帧特征也无法识别，再考虑修改视觉或时间表示。

### problem：不知道解说质量主要被哪个模块拖累

问题可能来自视觉编码、时间信息处理、Q-Former、projector、Llama 或最后的解码方法。目前 Q-Former 只是首要候选，还不是最终结论。

**sol：**

保存每个关键阶段的中间结果，每次只替换一个模块的输出，其他部分保持不变。哪个模块被替换后稳定减少遗漏和编造，就优先改哪个模块；如果多个模块都有影响，就分别报告它们的作用。

### problem：解码方法可能让解说过短、重复或编造

即使模型内部已经有正确视觉信息，beam search、sampling、受限词表等设置也可能改变最终输出。

**sol：**

固定同一个模型和输入，只比较不同解码设置。重点观察事件覆盖、编造、重复和长度，不只比较文本分数。

## SoccerFactory

SoccerFactory 当前 pipeline：

```text
bbox_detector
→ reid
→ track
→ pitch / calibration / apply_camera_params
→ legibility / jersey_number_detect
→ tracklet_agg
→ team / team_side
→ Refiner
→ conversion / evaluation
```

### problem：人物检测错误会污染后续所有字段

漏检、误检或人物框不准，会继续影响 ReID、跟踪、角色、球队、号码和球场坐标。

**sol：**

先在少量人工标注帧上单独检查人物框，分别统计远景、遮挡和画面边缘人物。检测不可靠的框不直接进入后续属性判断。

### problem：普通球员、门将和裁判目前无法可靠地区分

现有角色结果会漏掉门将和裁判。不同角色模块输出的 `role_confidence` 含义也不一样，不能直接放在一起比较。

**sol：**

为普通球员、门将和裁判建立轨迹级人工标签。模型同时查看人物裁剪、完整画面、球场位置和多帧信息；看不清时输出 `unknown`。不同模型分别保存自己的分数，不再共用含义不清的置信度字段。

### problem：同一个 `track_id` 可能跨越不同人物

跟踪先连接球员 A，丢失目标后又把球员 B 接到同一个 ID，会导致球队、角色、号码和坐标互相冲突。

**sol：**

检查同一轨迹中的外观、球衣颜色、号码和位置是否突然变化。发现明显变化、长时间丢失或镜头切换时切断轨迹，再分别分配新 ID。角色、球队和号码只在确认属于同一人的轨迹片段内聚合。

### problem：目前无法可靠判断人物所属球队

SNGS-10004 中现有球队聚类形成了 46/3 条轨迹的严重失衡，说明 ReID 特征没有可靠地区分两种球衣。

**sol：**

先排除裁判和低质量人物框，再使用多帧上半身球衣颜色区分两队。`left/right` 只负责给已经形成的两队命名，不能用来修复错误聚类。看不清或结果冲突时保留 `unknown`。

### problem：球衣号码识别可能不完整或被错误轨迹污染

号码不是每帧都清楚可见。如果先发生 ID Switch，再做整条轨迹投票，可能把两个人的号码合在一起。

**sol：**

先判断号码是否可读，只在清楚帧上运行 OCR；完成轨迹切分后，再在同一人物片段内做号码投票。无法确认时输出 `unknown`，不要强行给号码。

### problem：球场坐标是否准确仍然未知

坐标落在球场范围内，只能说明格式和数值合法，不能说明人物真实位置正确。相机标定误差和 ID Switch 都会造成坐标跳动。

**sol：**

人工标注少量球场点和人物脚点，分别检查相机标定误差与人物位置误差。先确认 Refiner 前的坐标质量，再评价 Refiner 是否真正改善结果。

### problem：Refiner 没有显示出稳定的坐标改善

当前固定样本上，Refiner 后的轨迹抖动反而明显增加。没有坐标真值，所以还不能判断绝对精度是否变好或变差。

**sol：**

在有坐标真值的样本上直接比较 Refiner 前后误差。只有 Refiner 确实降低位置误差时才采用；否则保留原坐标，或只接受通过质量检查的 Refiner 修改。

### problem：字段都生成了，不代表 SoccerFactory 已经能输出准确标签

当前链路可以生成检测框、ID、角色、球队、号码和坐标等字段，但其中多个字段还没有可靠的人工真值评价。

**sol：**

建立一个小规模人工审核集，分别评价人物框、ID、角色、球队、号码和坐标。每个阶段先单独通过，再检查完整链路中这些字段是否互相一致。

## 当前优先顺序

1. 解说：先完成人工事实表和现有 Q-Former 干预结果的盲审。
2. SoccerFactory：先检查并切分 ID Switch，因为它会污染角色、球队、号码和坐标。
3. 然后解决角色识别和球队归属。
4. 最后在有真值的样本上评价号码、坐标和 Refiner。
