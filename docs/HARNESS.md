# SoccerMaster Harness 协议

本文档只规定正式 Gate 如何执行和判定。它不替代 `AGENTS.md` 的安全与授权规则，也不记录当前进度或历史运行结果。

## 1. 适用范围

只有会形成或改变 Gate 通过/失败结论的运行才使用完整 Harness。以下工作不使用完整模板：

- 普通研究实验和消融；
- 故障定位、静态准备和运行前预检；
- 文档、可视化和只读分析；
- 不改变 Gate 状态的单样本或小规模诊断。

这些工作按 `AGENTS.md` 的 A/B 级规则记录。它们可以为 Gate 提供证据，但不能因为使用了大量检查就自动成为 Gate，也不能事后补造审计字段来改写当时的结论。

Harness 不要求单元测试覆盖率、CI、全仓库格式化、通用异常输入防御或完整证据链。每项检查必须对应当前 Gate 的具体风险；检查失败如果不会改变本次判定，就不执行。

## 2. 文档职责

```text
AGENTS.md                         长期规则、授权边界和验证分级
docs/HARNESS.md                   正式 Gate 的判定协议
REPRODUCTION_STATUS.md            当前状态、历史结论和兼容例外
reports/                          原始日志和机器结果
docs/future_improvements/         尚未验证的研究假设
```

发生冲突时先服从 `AGENTS.md`。当前事实以 `REPRODUCTION_STATUS.md` 和原始证据为准。

## 3. 基本原则

- 一个 Gate 只证明预先写明的范围。
- 成功和失败由必要断言与退出码决定。
- 不得为了通过而改变模型、数据、精度、设备、batch size、任务或 checkpoint。
- 不得静默跳过必需资产、样本、任务头或失败的 rank。
- 前一 Gate 通过不证明或授权后一 Gate。

## 4. 最小 Gate 记录

运行前只需写清：

```text
Gate 与目标:
用户授权范围:
输入、模型、checkpoint 和关键配置:
设备、dtype、batch size 和数据范围:
执行命令:
必要断言及通过/失败条件:
timeout 与心跳（仅长时间命令）:
输出路径:
明确不验证的内容:
```

运行后只需补充：

```text
退出码:
必要断言和核心结果:
日志与结果路径:
实际发生的 fallback、异常或语义变化:
结论和未验证范围:
```

没有适用内容的字段不填写。只有后续章节明确触发的专项风险，才增加相应记录。

## 5. 通过与失败

Gate 通过必须同时满足：

1. 前置条件满足，输入和命令可定位。
2. 进程在 timeout 内以退出码 0 结束。
3. 所有必要断言通过。
4. 没有未声明的 fallback、跳过或实验语义变化。
5. 日志和结果存在，并明确写出未验证范围。

以下情况不能判定通过：

- 只有“没有报错”，没有检查目标输出；
- 捕获错误后继续运行并返回 0；
- 缺少资产时换样本、少跑组件或少跑任务；
- 实际环境、配置或 checkpoint 与记录不一致；
- 外部中止、超时或多 rank 控制流不一致，但原因没有定位。

## 6. 检查如何选择

正式 Gate 始终记录入口命令、实际 Python、关键输入身份、数据范围、设备、输出和日志。其余检查按风险启用：

- 代码版本和相关 dirty 文件：代码变化会影响结论或需要精确复跑时记录。
- 依赖版本：环境、ABI 或跨机器兼容是当前问题时记录。
- resolved config：配置会改变实验语义时记录相关字段，不默认保存整份重复快照。
- seed、rank、dtype 和确定性设置：随机性、训练、分布式或重复性是判定内容时记录。
- 文件大小或 hash：只用于资产身份容易混淆、疑似损坏、跨机器传输、不可重建转换、checkpoint 或 exact resume。
- CPU/GPU 峰值和分阶段耗时：只用于资源安全、容量判断或性能结论。

默认不做单元测试覆盖率、全仓库测试、格式化、CI、全量 AST/导入/链接扫描、普通输出 hash 或与已观察风险无关的异常输入防御。

## 7. 数据与训练专项要求

只有 Gate 涉及数据入口、增强、loss 或训练接口时，才检查相关内容：

- batch 的必需字段、shape、dtype、device 和维度含义；
- 坐标系、归一化、padding 及空标注处理；
- 几何增强后图像与框、线、关键点和相机参数是否同步；
- 一个 optimizer step 包含的任务、batch、loss 权重和更新边界。

必需资产缺失、损坏或无法解析时应尽早失败；除非协议事先允许，不得在 DataLoader 中静默丢弃样本。没有对应风险时，不为假设性的异常输入建立通用防御或测试矩阵。

## 8. 随机性、恢复和 checkpoint

本节只适用于 G6–G9 或其他明确验证训练恢复的 Gate。

普通可重复训练记录实际使用的 seed 和采样策略。只有验证 exact resume 时，才要求保存和恢复模型、optimizer、scheduler、AMP scaler、训练进度、必要 RNG、sampler 和任务调度状态。

exact resume 必须证明从同一保存点恢复后，下一批输入、loss 和参数更新满足预先定义的等价条件。允许定义数值容差的恢复只能称为 `functional_resume`；具体比较对象和容差写在对应 Gate 的协议或结果中，不在本文件固化历史运行参数。

只有新写入且需要自动恢复的 checkpoint 才要求事务式保存：先写同文件系统临时目录，检查必需文件和可读取性，最后写完成标记并原子改名。manifest 只记录恢复所需的组件、训练状态、配置和基础权重身份；除非验证位级一致性或资产身份，不要求逐文件 hash。

历史 checkpoint 可以做兼容加载，但必须准确说明它包含哪些状态，不能把部分权重描述为完整训练恢复。

## 9. 分布式专项要求

本节只适用于多 rank Gate。

- 所有 rank 必须以兼容顺序进入 collective。
- 空 batch、坏样本、OOM 或任务失败时，不允许只有部分 rank 静默跳过。
- 长时间运行的心跳应包含 rank、step、task 和当前阶段。
- hang 或 timeout 应定位各 rank 最后阶段；不能只增加 timeout 后宣称问题解决。

## 10. 性能结论

只有要形成性能或容量结论时，才记录相关分阶段耗时、吞吐、CPU 内存和 GPU 显存。分阶段只覆盖当前瓶颈所需的环节，不要求每次都测量完整数据流。

吞吐比较必须同时固定并报告 batch size、帧数、分辨率、任务组合、dtype、worker 和设备。单独的 GPU 利用率不能解释性能瓶颈。

## 11. 失败记录

失败报告只需写清直接错误、发生阶段、已完成范围和是否留下本次进程。固定分类标签是可选字段，不要求为普通失败建立独立 taxonomy。

直接原因未知时，保留已有日志，并给出一个能缩小范围的只读或最小动作；不自动扩大成全链路审计。

## 12. Gate 最小证明范围

- **G0**：代码、配置、数据和权重已定位，访问边界明确。
- **G1**：目标 Python 和必要依赖满足导入或版本要求；不证明模型可运行。
- **G2**：完整 checkpoint 按目标策略加载，组件和 keys 检查通过；不证明 forward。
- **G3**：规定形状的随机张量完成 forward，输出结构、shape 和有限性通过。
- **G4**：一个固定真实视频通过完整输入和推理路径，并保存可检查结果。
- **G5**：固定小规模清单完成评估，产生结构完整的指标与预测。
- **G6**：固定微型数据可以按预期过拟合，标签、梯度和优化器链路成立。
- **G7**：单任务训练、恢复和评估协议成立。
- **G8**：小规模多任务调度、梯度、分布式行为和指标记录成立。
- **G9**：完整训练完成，并满足事先定义的资源、评估和恢复要求。
- **G10**：SoccerFactory 分支在独立范围内完成对应阶段，不反向污染基线。

Gate 顺序、当前授权例外和长期安全边界只在 `AGENTS.md` 维护；当前状态和历史结果只在 `REPRODUCTION_STATUS.md` 维护，本文件不重复记录。

每个 Gate 完成后更新 `REPRODUCTION_STATUS.md` 并停止。任何下一 Gate 都需要新的用户指示及适用的资源授权。
